title: Webhook V2
---

Webhook Events enable real-time communication between SeerBit and your application. When specific activities occur within the payment ecosystem such as transactions, refunds, wallet movements, disputes, or virtual account events, SeerBit sends a structured notification to your configured webhook endpoint.<br/>

Webhook V2 provides a standardized acknowledgment protocol designed to ensure reliable delivery, traceability, and idempotent handling.

## 1. Overview

A webhook is an HTTP callback: a POST request sent to your server when an event happens. When your webhook URL is configured in SeerBit, the platform automatically notifies your system whenever a subscribed event occurs.

##### When your endpoint receives a webhook request:

1. Your server must respond with a 200 OK
2. Your server must return a JSON acknowledgment object
3. SeerBit considers the event delivered upon receiving a valid acknowledgment
4. Your server processes the event

If the acknowledgment is missing, invalid, or delayed, SeerBit retries delivery.

## 2. Delivery Architecture

- **Event Triggered**<br/>
  A payment, refund, settlement, dispute, or wallet event occurs.

- **Webhook Preparaion**<br/>
  SeerBit constructs the event payload and generates an optional acknowledgment reference.

- **Delivery Attempt**<br/>
  A POST request is sent to your Webhook URL over HTTPS.

- **Merchant Processing**<br/>
  Your server receives the request and process the event.

- **Acknowledgment Response**<br/>
  Your server returns:

```json
{
  "ackReference": "...",
  "status": "received"
}
```

- **Confirmation**<br/>
  SeerBit mark the Webhook as delivered.

- **Retry (if acknowledgment fails)**<br/>
  Multiple retries occur at increasing intervals.

This handshake ensures that events are not lost and can be processed reliably and idempotently.

## 3. Webhook Request Format

HTTP Method - <Badge color="blue">POST</Badge><br/>
Content-Type - `application/json`

| Header                   | Type     | Description                                                             | Requred  |
| ------------------------ | -------- | ----------------------------------------------------------------------- | -------- |
| Content-Type             | `string` | Always application/json                                                 | Yes      |
| X-Expected-Ack-Reference | `string` | A unique reference that must be returned in the acknowledgment response | Optional |

Body - A JSON object containing event metadata and associated data specific to the event type.

## 4. Acknowledgment Response (Required)

To confirm receipt of a webhook event, your server must return:

- HTTP 200 OK
- A JSON Object
- Within 5 seconds

```json Acknowledgement JSON Structure
{
  "ackReference": "<value-or-fallback>",
  "status": "received"
}
```

##### Field Definitions

| Field        | Type     | Description                                                                                                                                         |
| ------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| ackReference | `string` | Must match the value from the X-Expected-Ack-Reference header if provided. If the header is absent, your system must generate a fallback reference. |
| status       | `string` | Must always be "received".                                                                                                                          |

SeerBit requires this acknowledgment to validate that your system has successfully accepted the event.

## 5. Retry Logic

If your server:

- Returns non-200 status
- Responds with an invalid acknowledgment
- Times out (exceeds 5 seconds)
- Is unreachable

**…SeerBit will retry delivery**.

#### Retry Intervals

Typical retry sequence:

1. 30 seconds
2. 2 minutes
3. 10 minutes
4. 30 minutes
5. 1 hour (final retry)

**If all attempts fail, the webhook is marked as undelivered**.

## 7. Sample Implementations

Below are full sample implementations demonstrating how to handle webhook V2 acknowledgments.

<CodeGroup>

```python Python(FastAPI)
from fastapi import FastAPI, Request, Header
from fastapi.responses import JSONResponse
import time

app = FastAPI()

@app.post("/webhook")
async def receive_webhook(request: Request, x_expected_ack_reference: str = Header(default=None)):
    body = await request.body()
    print("Received V2 webhook:", body.decode())
    print("Received Ack Reference from header:", x_expected_ack_reference)

    if not x_expected_ack_reference:
        x_expected_ack_reference = f"fallback-ref-{int(time.time() * 1000)}"

    return JSONResponse({
        "ackReference": x_expected_ack_reference,
        "status": "received"
    })
```

```javascript Node.JS(Express)
const express = require('express');
const app = express();

app.use(express.json());

app.post('/webhook', (req, res) => {
  const body = req.body;
  let ackRef = req.headers['x-expected-ack-reference'];

  console.log('Received V2 webhook:', JSON.stringify(body));
  console.log('Received Ack Reference from header:', ackRef);

  if (!ackRef) {
    ackRef = `fallback-ref-${Date.now()}`;
  }

  res.json({
    ackReference: ackRef,
    status: 'received',
  });
});
```

```java Java(Spring Boot)
@RestController
public class WebhookController {

    @PostMapping("/webhook")
    public ResponseEntity<?> receiveWebhook(
        @RequestBody String body,
        @RequestHeader(value = "X-Expected-Ack-Reference", required = false) String ackRef) {

        System.out.println("Received V2 webhook: " + body);
        System.out.println("Received Ack Reference from header: " + ackRef);

        if (ackRef == null || ackRef.isEmpty()) {
            ackRef = "fallback-ref-" + System.currentTimeMillis();
        }

        Map<String, String> response = new HashMap<>();
        response.put("ackReference", ackRef);
        response.put("status", "received");

        return ResponseEntity.ok(response);
    }
}
```

## 8. Security Considerations

Although webhook V2 does not require a signature by default, the following best practices are strongly recommended:

### Inbound Request Validation

- Enforce HTTPS
- Reject requests not coming from approved IP ranges (if applicable)
- Validate Content-Type = application/json
- Validate the structure of the payload

### Idempotency

Your webhook consumer must ensure duplicate events are not processed twice.

##### Recommended approaches

- Use eventId field as a unique identifier
- Store processed event IDs in a database
- Check before applying business logic

### Logging

Log:

- Full payload
- Ack reference
- Processing time
- Errors and decisions

## 9. Testing Webhooks

##### To test locally

Use tools like:

- ngrok
- cloudflared tunnel
- localtunnel

This exposes your local server to receive webhook events.

##### Replay event

Your internal systems should allow replay during testing, especially for integration and QA teams.

## 10. Troubleshooting

##### Webhook not arriving

- Check that your URL is reachable publicly
- Check SSL certificates
- Verify URL configuration in SeerBit dashboard
- Confirm firewall/NAT rules

##### Webhook arrives but no retries

Your server may be returning 200 OK with incorrect acknowledgment structure.

##### Event processed twice

Implement idempotency based on the eventId field.

##### 400 or parsing errors

Ensure your endpoint expects JSON and does not require authentication unless pre-agreed.
